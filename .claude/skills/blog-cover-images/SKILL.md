# Blog cover images

Generates cover images for posts in `src/content/post/<slug>/`, in the site's
monochrome two-tone style.

## Before you start

Read the post. The whole point of these covers is that the image encodes the
post's actual argument — not a generic AI-slop visual. Find the one claim the post
is really making, then find the simplest mark that states it.

Good examples from the existing set:

| post | argument | mark |
|---|---|---|
| Postgres checkpointer | checkpoint rows are hot state that must age out | a row of squares fading from solid to a broken outline |
| ReAct from scratch | reasoning and acting form a closed loop | a broken ring, three points, one direction wedge |
| Notes on Building Effective Agents | a workflow follows a fixed path, an agent picks its own | a straight dotted line beside a winding looping one |
| Remote MCP on EC2 | one server reached over a long-lived stream | dots travelling a line into a square inside a dashed perimeter |
| Deep Agents CLI | work is delegated to sub-agents, and one link was broken | a circle branching to five, one connector cut |

The two strongest are ReAct and Deep Agents, because the *gap* in the drawing is
the content: the `PAUSE` in the loop, and the `interrupt_on` that silently failed
to propagate to sub-agents. Look for that kind of coincidence between form and
finding — a hole, a break, a thinning, an asymmetry that means something.

## Requirements

- `OPENROUTER_API_KEY` in the environment. If it is missing, stop and ask — do not
  try to generate without it.
- Roughly $0.14 per image. Generate one to calibrate before doing a batch.

## Running it

The generator lives at `.claude/skills/blog-cover-images/generate.sh`, with the
post-processing step beside it. Both must stay in the same directory.

```bash
export OPENROUTER_API_KEY=sk-or-...

# One post. SUBJECT is the per-image description (see below).
SUBJECT="$(cat subject.txt)" .claude/skills/blog-cover-images/generate.sh <slug> <dest-filename>
```

`<dest-filename>` is the filename inside the post folder, because it is not
uniform across posts — most are `cover.png`, but `deploy-mcp-server-remote-aws`
uses `images/cover.png` and `scaling-langgraph-postgres-checkpointer` uses
`cover-langchain-checkpointer.png`. Check the post's frontmatter `coverImage.src`.

Output goes to `./out/`, never straight into the repo. Two files per run:
`<slug>.raw.<ext>` (exactly what the API returned) and `<slug>.png` (normalised).
Install the normalised one.

## Writing the SUBJECT

One paragraph, present tense, describing only *what is in the frame*. Be specific
about count, position and which element is solid versus outline — the model
follows concrete instructions and invents when left vague. State what is NOT
there ("nothing else in the frame") to keep it reductive.

Do not describe style in the SUBJECT. The shared style block in `generate.sh`
handles that, and it must stay identical across every image or the set stops
looking like a set.

## After generating

1. **Look at the image.** Read the PNG. Do not report success without viewing it.
2. Verify it: `node .claude/skills/blog-cover-images/verify.cjs out/<slug>.png` —
   checks format, dimensions and that all four corners are exactly `#1d1f20`.
3. Build the light-mode variant — see below. Every cover needs both.
4. Confirm the current cover is committed in git (`git diff --quiet HEAD -- <path>`)
   so it can be recovered, then copy the new files over it.
5. Update `coverImage.alt` in the post's frontmatter to describe the *new* image,
   and set `coverImage.srcLight` to the light variant. Stale alt text describing
   the old artwork is the easiest thing to forget.
6. If the dev server is running, clear the metadata cache or Astro keeps serving
   the old dimensions: `rm -rf .astro node_modules/.astro` and restart.

## Light and dark variants

Each cover ships as two files: the dark one generated by the model, and a light one
derived from it. **Do not generate the light version separately.** The art is flat
two-tone, so the light variant is a deterministic recolour — free, instant, and
guaranteed to be the same drawing, so toggling the theme doesn't swap the artwork
out from under the reader.

```bash
node .claude/skills/blog-cover-images/make-light-variant.cjs \
  src/content/post/<slug>/cover.png \
  src/content/post/<slug>/cover-light.png
```

Naming convention: the light file is the dark filename with `-light` appended, in
the same folder.

The light palette also comes from `src/styles/global.css`, `:root`:

- background `#fafafa` — `--theme-bg`
- marks `#121212` — `--theme-accent-2`

Frontmatter declares both:

```yaml
coverImage:
  src: "./cover.png"
  srcLight: "./cover-light.png"
  alt: "..."
```

`srcLight` is optional in the schema (`src/content/config.ts`). Without it,
`src` is shown in both themes — which is what you want to avoid, since a charcoal
image on a near-white page reads as a pasted block.

`src/components/blog/Hero.astro` renders both and swaps them with Tailwind's
`dark:` variant (`hidden dark:block` / `dark:hidden`). It cannot use
`<picture media="(prefers-color-scheme: dark)">`, because the theme here is a class
on `<html>` set by the toggle, not the OS preference — a media query would ignore
the user's choice. The cost is that both files are fetched; at ~50–110KB each that
is still far below the 1.6MB the originals weighed.

If you ever want genuinely *different* compositions per theme rather than a
recolour, run `generate.sh` twice with different SUBJECTs and skip
`make-light-variant.cjs`. Nothing enforces that the two files are the same drawing.

## Style, and why it is what it is

Two flat tones, hand-drawn, radically reductive. Derived from the Anthropic
engineering blog covers, whose SVGs are plain single-colour `fill` paths with no
gradients, no strokes and deliberately wobbly geometry.

The two tones are the site's own palette values, from `:root.dark` in
`src/styles/global.css`:

- background `#1d1f20` — `--theme-bg`
- marks `#ededed` — `--theme-accent-2`

Format is 16:9, not the square Anthropic uses. `src/components/blog/Hero.astro`
renders the cover with no fixed width inside a 768px container, so a square would
be 768×768 and push the title off screen.

Background is solid, not transparent. Gemini returns PNG or JPEG with no usable
alpha, and a fixed background means picking a side: charcoal blends into dark mode
and reads as a deliberate dark card in light mode, which is the better trade.

## Why the normalisation step exists

The raw generation is wrong in two ways that matter, both fixed deterministically
by `normalize-cover.cjs` rather than by re-rolling the generation:

- **The charcoal drifts.** Asking for `#1d1f20` yields something like `#212224`.
  Close, but on the page it produces a visible edge instead of blending.
- **The file is enormous.** ~1.6MB of JPEG compression noise for a two-tone flat
  image. After normalising, 50–110KB.

It finds the two histogram modes, clamps just inside each to flatten the noise
without eating the antialiased edge that gives the stroke its hand-drawn quality,
remaps onto the exact palette values, and re-encodes as PNG. If an image turns out
not to be two-tone it warns and passes the raw file through untouched rather than
wrecking it.

## Known gotchas

- The API returns **JPEG** despite the model being an image model. Honour
  `data[0].media_type` for the raw file's extension; do not assume `.png`.
- `generate.sh` writes `out/` relative to the current directory. Run it from the
  repo root, or set `OUT=`.
- `normalize-cover.cjs` needs `sharp`, which comes from this repo's
  `node_modules` via `NODE_PATH`. Run `pnpm install` first if it is missing.
- Prompt adherence is approximate. Asking for three dots can yield two. If exact
  counts matter, regenerate — it is another $0.14.
